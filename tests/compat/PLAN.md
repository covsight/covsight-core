# NCDB Cross-Implementation Compatibility Test Plan

## Problem Statement

Three independent implementations can now read and write the NCDB `.cdb` format:

| Implementation | Language | Writer | Reader |
|---|---|---|---|
| `python/` | Python 3 | `NcdbWriter` | `NcdbReader` |
| `ts/` | TypeScript (Node.js) | `NcdbWriter` | `NcdbReader` |
| `c/` | C99 | `ncdb_Write` | `ncdb_Open` |

Each implementation has its own language-native unit tests, but there is currently
no systematic cross-compatibility test suite that verifies every writer × reader
pairing with precise data-integrity checks.

## Goals

1. Prove all 9 writer × reader pairs (3 writers × 3 readers) produce identical data.
2. Exercise every serializable NCDB feature in every pair.
3. Provide committed golden fixture files that act as format regression guards.
4. Integrate naturally into the existing test commands
   (`pytest`, `npm test`, `ctest`), not requiring a new orchestration tool.
5. Be easy to extend as new features are added.

## Out of Scope

- Performance / benchmark tests (already in `bench/`)
- Fuzzing / malformed-input hardening
- UCIS API semantic tests (already in `python/tests/`, `ts/tests/`)

## Design Decisions

### Orchestration: pytest as the hub

pytest is chosen because:
- Python is already the "glue" language in the C tests (`verify_python_read.py`)
- Subprocess calls to `node` and compiled C binaries are trivial
- Parametrized `@pytest.mark.parametrize` cleanly expresses the N×N matrix
- `conftest.py` fixtures handle build-once / use-many for compiled artifacts
- A single `pytest tests/compat/` command covers all cross-compat cases

TS-native (jest) and C-native (ctest) tests remain for unit-level checks; the
`tests/compat/` suite adds the cross-implementation layer on top.

### Comparison: JSON wire format ("dump" helpers)

Each implementation exposes a **dump helper** that reads a `.cdb` file and
emits a canonical JSON representation.  pytest compares these JSON documents.
This approach:
- Avoids fragile text-output parsing
- Makes failures immediately readable
- Lets Python act as reference reader in all cases (Python reads its own JSON)

**Canonical JSON schema** (see `schema.md` for full spec):

```json
{
  "scopes": [
    {
      "name": "cg_0",
      "type": 8388608,
      "items": [
        { "name": "b0", "coverType": 131072, "count": 42, "atLeast": 1 }
      ],
      "children": [ ... ]
    }
  ],
  "history": [
    { "name": "smoke", "kind": "TEST" }
  ]
}
```

Fields with default values are always emitted so comparisons are unambiguous.

### Golden fixture files

A set of committed `.cdb` files lives in `tests/compat/golden/`.
Each fixture is generated by one specific implementation and checked in.
The `generate_golden.py` script regenerates them when the format evolves.

Golden files serve as **format regression guards**: if any reader's output
differs from the expected JSON, the test fails.

## Test Scenarios (Fixtures)

Each scenario defines a coverage database with specific features to exercise.
Scenarios are encoded as Python dicts in `conftest.py` and as functions in the
helper scripts.

| Scenario | Features exercised |
|---|---|
| `minimal` | Single CG → CP → 1 bin, default everything |
| `basic` | DU_MODULE + INSTANCE, 2 CGs, 3 CPs each, 5 bins, varied counts |
| `at_least` | Non-default `atLeast` (2) across all bins in a scope |
| `toggle` | BRANCH scope with `0 -> 1` / `1 -> 0` implicit bins |
| `source_info` | `file_id`, `line`, `token` present on scopes |
| `history` | TEST history node with `userName`, `seed`, `toolCategory` |
| `cross` | CROSS scope referencing two coverpoints |
| `deep` | 5-level deep nesting, 50 scopes, no cover items until leaf |
| `empty` | DB with no scopes, no history |
| `full` | All of the above in a single DB |

## Detailed Test Plan

### Module: `test_golden.py` — Golden file regression

**Purpose**: Guard against unintended format changes.  Every committed golden file
must be readable by all three implementations, producing output that exactly
matches the expected JSON (stored as `golden/<file>.json`).

**Tests**:
```
test_golden_py_reads_golden[py_minimal]
test_golden_py_reads_golden[py_full]
test_golden_py_reads_golden[ts_full]
test_golden_py_reads_golden[c_full]
test_golden_ts_reads_golden[py_full]
test_golden_ts_reads_golden[ts_full]
test_golden_ts_reads_golden[c_full]
test_golden_c_reads_golden[py_full]
test_golden_c_reads_golden[ts_full]
test_golden_c_reads_golden[c_full]
```

**Approach**:
- Parametrize: `@pytest.mark.parametrize("cdb_file", golden_cdb_files())`
- Reader trio: Python reads directly; TS and C via dump-helper subprocess
- Compare output against committed `<file>.json` sidecar
- Sidecar generated by Python (canonical reader) when `generate_golden.py --update` is run

**Failure semantics**: A golden test failure means either the file format changed
(intentional format evolution → regenerate golden) or a reader has a bug.

---

### Module: `test_cross_write_read.py` — Write-then-read cross-compatibility

**Purpose**: Each implementation writes each scenario; all three readers verify
the data is identical to what was written.

**Parametrization**:
```python
@pytest.mark.parametrize("writer", ["python", "typescript", "c"])
@pytest.mark.parametrize("scenario", SCENARIOS)
def test_cross_read(writer, scenario, tmp_path, helpers):
    cdb = helpers.write(writer, scenario, tmp_path)
    ref_json  = helpers.read_python(cdb, scenario)
    ts_json   = helpers.read_ts(cdb)
    c_json    = helpers.read_c(cdb)
    assert ts_json == ref_json
    assert c_json  == ref_json
```

This generates `len(writers) × len(scenarios)` test cases (3 × 10 = 30), each
asserting all readers agree with the Python reference.

**Note**: Python is always the reference reader because it was first and has the
most complete tests.  Disagreements indicate a bug in the TS or C reader.

---

### Module: `test_fidelity.py` — Per-feature data integrity

**Purpose**: Precise value verification for each feature in isolation, not just
"readers agree" but "readers produce the expected values".

**Tests** (example subset):

```python
def test_scope_names_preserved(writer):
    """All scope names survive write → read."""

def test_cover_item_counts(writer):
    """Cover item count values are exact bigint-compatible integers."""

def test_atLeast_default_not_written(writer):
    """atLeast=1 (default for CVGBIN) does not inflate file size."""

def test_atLeast_nondefault_roundtrips(writer):
    """atLeast=2 is preserved for all items in a scope."""

def test_toggle_bin_order(writer):
    """'0 -> 1' and '1 -> 0' bins are present and ordered correctly."""

def test_toggle_bin_counts(writer):
    """Toggle bin counts (3, 4) are preserved exactly."""

def test_history_node_kind(writer):
    """History node kind (TEST=0) is preserved."""

def test_history_node_name(writer):
    """History node name is preserved."""

def test_source_info_line_token(writer):
    """file_id, line, token are preserved when source info is present."""

def test_cross_pointed_scopes(writer):
    """Cross coverpoint references are preserved as scope names."""

def test_scope_type_values(writer):
    """ScopeTypeT enum values are preserved exactly (e.g. COVERGROUP=0x800000)."""

def test_du_instance_link(writer):
    """INSTANCE scopes correctly reference their DU_MODULE by name."""
```

Each test is parametrized over `["python", "typescript", "c"]` for the writer.
Verification always reads back with all three readers.

## Helper Implementation Plan

### `helpers/ts_dump.mjs`

```
Usage: node ts_dump.mjs read <file>    → JSON to stdout
Usage: node ts_dump.mjs write <scenario> <file>  → writes .cdb
```

Depends on `ts/dist/` (built by `npm run build`).  The `conftest.py` fixture
checks for `ts/dist/index.js` and raises a descriptive skip if not built.

Scenarios are implemented as functions matching the Python scenario definitions.

### `helpers/c_dump.c` + `helpers/Makefile`

```
Usage: ./c_dump read <file>    → JSON to stdout
Usage: ./c_dump write <scenario> <file>  → writes .cdb
```

Depends on `libncdb.so` (built by cmake).  `conftest.py` builds `c_dump`
automatically if `c/build/libncdb.so` exists.  If `libncdb.so` is absent, the
C-writer and C-reader tests are skipped with a descriptive message.

The `Makefile` target:
```makefile
c_dump: c_dump.c
    gcc -O2 -o c_dump c_dump.c \
        -I../../c/include -I../../c/src \
        -L../../c/build -lncdb -Wl,-rpath,../../c/build
```


## `generate_golden.py`

```
Usage: python generate_golden.py [--update]
```

- Without `--update`: verifies golden files match expected JSON (same as pytest golden tests)
- With `--update`: regenerates all `golden/*.cdb` and `golden/*.json` files

Each golden `.cdb` is written by its named implementation.  The `.json` sidecar
is always generated by the Python reader (canonical).

## `schema.md` — Canonical JSON Schema

Full spec for the JSON format emitted by all dump helpers:

```
{
  "format": "ncdb-dump-v1",
  "scopes": [ <scope>, ... ],         // top-level scopes only; rest nested
  "history": [ <history_node>, ... ]
}

<scope> = {
  "name": string,
  "type": integer,                    // ScopeTypeT numeric value
  "items": [ <item>, ... ],
  "children": [ <scope>, ... ]
}

<item> = {
  "name": string,
  "coverType": integer,               // CoverTypeT numeric value
  "count": integer,                   // always non-negative
  "atLeast": integer                  // always present, even if default (1)
}

<history_node> = {
  "name": string,
  "kind": "TEST" | "MERGE" | "ACCUMULATED" | "GENERICBIN"
}
```

Rules:
- All integers are decimal (not hex)
- `count` is always a 64-bit unsigned value serialized as JSON number
  (if > 2^53, use string — but benchmarks stay within safe range)
- Field order in each object is fixed (alphabetical) for deterministic diffs

## Integration with Existing Test Commands

### Python
```bash
cd python
pytest tests/              # existing tests unchanged
pytest ../tests/compat/    # new cross-compat suite
```

### TypeScript
Jest tests are unchanged.  The compat suite does not add jest tests.

### C (ctest)
The existing `test_python_read` CMake test already verifies C→Python.
The compat suite supersedes it with broader coverage, but both are kept.

### CI
A new CI step runs `pytest tests/compat/` after all three builds complete:
```yaml
- name: Build C library
  run: cmake -S c -B c/build && cmake --build c/build
- name: Build TypeScript
  run: cd ts && npm ci && npm run build
- name: Cross-compatibility tests
  run: pytest tests/compat/ -v
```

## Resolved Decisions

1. **C writer for all scenarios**: `c_dump write` links against both `ncdb.h`
   and the internal `ncdb_impl.h`. This is acceptable for a test binary.

2. **History node detail**: Fidelity tests cover name + kind only for now.
   Full `TestData` fields (`userName`, `seed`, `toolCategory`) are tracked as a
   cross-implementation gap in `docs/cross-impl-todo.md`.

3. **Cross reference representation**: JSON uses `"crossedPoints": ["cp_a", "cp_b"]`
   (name list). Full coverpoint object-handle support is tracked in
   `docs/cross-impl-todo.md`.

4. **Source info in C**: The `source_info` scenario is Python/TS only until C is
   extended. Tracked in `docs/cross-impl-todo.md`.

5. **Count type**: Test scenarios use values ≤ 10^6 (safe JSON numbers for all
   three runtimes).
